# Remote anchor chain identity

Status: original design for Nock #11707, implemented by N11742–N11745 and shipped in v0.10.0. The released v0.9.3 client still uses v1 remote anchors. The current v2 commands and limits are documented in [audit log](../how-it-works/audit-log.md) and the [CLI reference](../reference/cli.md).

## Problem and boundary

The legacy v1 anchor signs `agent_id`, the SHA-256 fingerprint of the Ed25519 signing public key. The v1 client pushes it and fetches the latest anchor by that fingerprint (`internal/logging/anchor.go`, `internal/anchorclient/client.go`, `internal/cli/anchor_push.go`). Audit databases are per project (`internal/config/state.go`), but the default managed signing key is shared. A store that follows the v1 contract has one slot per key: a smaller project's legitimate push can get a 409, and its verification can report the larger project's anchor as `TRUNCATION`.

The goal is one independently monotonic remote anchor stream per audit chain, even when chains share a signing key. A chain ID must survive a project directory rename or move. It must be authenticated in the anchor and checked against the local chain before a row-count verdict is possible. Merely adding an unsigned URL parameter or hashing the project path would not meet those requirements.

## Proposed identity and v2 record

- Generate a 32-byte random `chain_id` with Go `crypto/rand` when a **new** audit chain is created; encode it as 64 lowercase hex characters. It is an opaque identifier, not a project name or path hash. Never derive it from `project.root`, the audit DB location, the key fingerprint, or the current directory. A rename or move retains the ID when the chain's trusted state is moved with it. Cloning a project to form a new independent chain requires an explicit fork that creates a new ID; copying the ID would keep the same remote stream.
- Persist the expected ID in an operator-owned chain-identity record in the trusted per-project audit state directory from `internal/config/state.go`, separate from `events.db`. Record the same ID in audit-chain metadata and require both copies to agree before emitting, pushing, or remotely verifying a v2 anchor. The identity record stays outside the fenced project even for a legacy `.nock/events.db` or a configured in-project database (`internal/config/config.go`). It is also outside a rollbackable database snapshot. A move must explicitly relocate the database and trusted identity record to their respective destination locations; a new path with an existing DB but no identity record must fail closed, not silently mint a replacement ID. This record is the local expected identity; the remote store is the off-box rollback pin. If an attacker can replace both trusted local state and the remote pin, this design cannot prove which project the operator meant.
- Keep `agent_id` as the signing-key fingerprint. Add `chain_id` and `version: 2` to the anchor. The v2 Ed25519 signature covers, in order, a new anchor-specific domain/version byte (proposed `0x06`), length-prefixed `agent_id`, the 32 decoded `chain_id` bytes, the 32 decoded `head_hash` bytes, `row_count` as unsigned big-endian 64-bit, length-prefixed `created_at`, and a 32-byte `legacy_anchor_digest` (all zeroes for a fresh v2 chain). The migration digest remains fixed for that chain's v2 anchors. JSON is transport only; exact canonical bytes are signed as in v1. Reject noncanonical IDs, unknown versions, invalid field lengths, and signatures before comparing counts. Keep v1's canonical bytes and verifier intact for explicit legacy-file checks (`internal/logging/anchor.go`).
- The server verifies the Ed25519 signature using the supplied public key and requires its fingerprint to equal the signed `agent_id`. It derives the storage key **only** from the verified `(agent_id, chain_id)` pair. The bearer token authorizes access but is not the chain identity. The client fetches using the expected local pair and checks that the returned signed pair equals it before verifying the local chain. Thus a valid anchor from another project using the same key is an identity mismatch, never a `TRUNCATION` verdict.

Define an anchor snapshot digest as SHA-256 of `"nocklock-anchor-snapshot-v1\x00"` for v1 (or `"nocklock-anchor-snapshot-v2\x00"` for v2), followed by that version's canonical signed bytes and the 64 decoded Ed25519 signature bytes. Use the raw 32-byte digest inside v2 canonical bytes; transmit `legacy_anchor_digest` and the compare-and-swap `expected_previous` as 64 lowercase hex characters in JSON. For a fresh v2 stream, `legacy_anchor_digest` is 64 zeroes. Verify the signature and canonical field encodings before computing a digest; JSON whitespace, field order, and base64 spelling do not change it. This is a digest of one signed anchor, not of the HTTP response envelope.

Use distinct v2 routes, for example `POST /api/nocklock/anchors/v2/` and `GET /api/nocklock/anchors/v2/{agent_id}/{chain_id}/latest/`. The v2 store must reject a URL/body identity mismatch and reject v2 records on its v1 route. A v2 client must not send v2 JSON to the v1 POST path: a v1 server could ignore `chain_id` and store it under `agent_id` alone. An unsupported v2 route is an actionable upgrade error, never permission to downgrade.

## Store updates and verification

The store owns one latest anchor per verified pair. Registration of a new pair is a separate explicit action conditional on its absence; an ordinary push never recreates a missing remote anchor. Each later push supplies the digest of the previously fetched v2 anchor as a compare-and-swap precondition. In one transaction, the server verifies the signature and pair, checks the expected previous digest, rejects a lower `row_count`, treats the same count and head as a no-op even if `created_at` differs, and rejects a different head at the same count. A higher count replaces only that pair's row. Before any push, including `anchor push --file`, the client verifies the candidate anchor's signature, local expected ID, and local head at its count. For a higher count it also verifies that the local chain reproduces the previous remote head at the previous count; a failed or unavailable preflight blocks the push. Compare-and-swap closes the race between that preflight and storage. A store with only signed heads cannot independently prove the missing intermediate rows, so it must not claim that it can; compromise of the signing key remains outside this protection.

Remote verification first authenticates the anchor and compares its signed pair with the trusted local pair. Only then does it apply the existing row-count and head-at-count checks in `internal/logging/anchor.go`: fewer local rows means `TRUNCATION`, a different head at the anchored count means tampering, and a matching prefix passes. A 404, unsupported endpoint, store error, absent trusted ID, malformed record, forged signature, or identity mismatch exits non-zero. `wrap`'s off-box push can retain its current warning and fail-open session-exit behavior, but it must never report a successful push on a conflict (`internal/cli/anchor_push.go`).

## Prune on an enrolled chain

`nocklock log --prune` (`internal/cli/log.go`, `internal/logging/logger.go`) rewrites the chain and lowers its `row_count`, so a pruned chain can neither satisfy the store's monotonic rule nor reproduce the previous remote head. Phase 2 therefore **refuses** `log --prune` on a v2-enrolled chain, with an actionable error naming the remote pin, until a separate prune-epoch transition is designed and gated. That transition would be a signed anchor carrying the previous anchor's snapshot digest and the authenticated prune boundary, accepted only as an explicit operator-acknowledged compare-and-swap. Refusing keeps the rollback pin fail-closed instead of locking it for good; a pruned chain is never silently re-pinned. Legacy v1 chains keep today's behavior (prune invalidates earlier anchors, `verify` prints a `NOTE`).

**Enrolled predicate.** The rule: prune is refused whenever the store might already hold a pin for this chain. A local "not enrolled" answer is allowed only when the chain has never been sent for registration. Once a registration has been sent, the chain never goes back to unenrolled. The trusted chain-identity record (see above) therefore carries a registration state:

- **none**: never sent for registration. Prune is allowed.
- **pending**: the client durably writes this state *before* it sends the first v2 registration. For the prune check, pending counts the same as enrolled.
- **enrolled**: the store confirmed the registration, or answered "already exists" for this `(agent_id, chain_id)` pair.

Pending becomes enrolled on success, or on an "already exists" answer for this pair. Any other outcome leaves it pending. There is no reconcile-to-none path and no clear-on-rejection path. A timeout, dropped connection, validation error, or crash after the request leaves pending in place, since the store may have committed. Registration and prune take the same lock on the trusted record, so neither can interleave with the other. Having a `chain_id` alone does not enroll a chain, so local-only users can still prune when no original registration request is retained. A retained request also blocks prune in state none: interruption between storing that request and writing pending must not destroy the signed prefix needed for exact replay. Unreadable or invalid request storage refuses prune too. The prune check reads only local trusted state and never asks the store. If `events.db` carries a `chain_id` but the trusted record is missing (the moved-project case), prune is refused too, with an error pointing at the state-move procedure. Until a prune-epoch transition lands, operators of an enrolled project who must bound log growth archive the old DB and enroll a fresh chain under a new explicit registration; the refusal error says so.

## Compatibility and explicit migration

| Client / store | Required behavior |
| --- | --- |
| v1 client / v1 store | Existing one-chain-per-key behavior and limitation. |
| v1 client / v2 store | Legacy v1 endpoint may serve an **unmigrated** key with the old limitation. Once any v2 stream is registered for that key, refuse v1 push and latest fetch with an upgrade response; a stale v1 latest must not appear to pass. Keep the legacy row for explicit migration. |
| v2 client / v1 store | V2 route is unavailable; fail with a server-upgrade message. Never fall back to the v1 endpoint or write a v2 anchor into its key-only slot. |
| v2 client / v2 store | Use the verified pair, conditional updates, and v2 verification. Explicitly migrated legacy chains also carry their fixed signed `legacy_anchor_digest`. |

Existing v1 anchors have **no project identity**, so neither client nor server may automatically assign one to a project. Migration is an explicit operator action:

1. Back up the legacy anchor and audit DB. Upgrade the store and client. Select the local project/chain that owns the legacy anchor; if multiple projects shared its key, do not infer ownership from the key or row count alone.
2. Obtain the stored v1 anchor through a migration-only read, verify its original signature and key fingerprint, and verify the chosen local chain reproduces its head at its row count. A shorter or divergent chain cannot claim it. Preserve the exact legacy anchor digest as the migration witness.
3. Explicitly enroll or retain the trusted local `chain_id` without changing the chain's rows. Sign the first v2 anchor with that ID and the legacy digest. An atomic server migration checks that the named legacy row still has the expected digest, validates both signatures and fingerprints, validates the signed v2 migration digest, rejects a v2 count below the legacy count, and requires the same head if counts are equal. For a higher v2 count, the client's step 2 prefix check is required; the server cannot prove that prefix from anchors alone. The server creates the `(agent_id, chain_id)` slot conditionally, marks the v1 key read/write-frozen for ordinary v1 clients, and retains the legacy row as history. A retry with the same pair and digest is idempotent; any different claim conflicts.
4. Run v2 remote verification and record its success before considering migration complete. If the old anchor belongs to a different project, stop; an unrelated project may register a **fresh** v2 stream only through an explicit server registration mode requiring operator acknowledgement that it has no legacy remote rollback history. When a v1 row exists for that key, the server rejects an ordinary fresh registration and requires this acknowledged mode; it retains the legacy row and freezes ordinary v1 access. Never overwrite or absorb the legacy anchor into that new stream.

An existing audit DB with no remote v1 anchor also needs an explicit one-time enrollment, not automatic ID creation during `push` or `verify`. The operator checks the signed local chain and signing-key fingerprint, confirms that no remote v1 anchor exists for that key or acknowledges that this project has no claim to an existing v1 anchor, and enrolls a new trusted ID without changing rows. The server registers its first v2 anchor conditionally. This establishes a new remote pin from that point forward; it does not claim earlier rollback protection. Until that first pin is stored, remote verification remains unavailable.

For a moved project, relocate the trusted identity record and DB together through an explicit state-move procedure, check that both still name the same ID, and verify against the existing remote pair before the next push. This includes a DB that remains inside the project while its identity record moves between trusted audit state directories. A newly discovered database with no identity record, an ID collision, or a copied ID with divergent history requires operator resolution; it cannot be repaired by silently generating or changing an ID. Local `verify --against-anchor` can continue to check an explicitly supplied v1 file with the v1 verifier, but the remote v2 path never treats v1 lookup as a success fallback.

## Implementation test plan

Use a disposable HOME/XDG state/config and a contract-compatible local HTTP store. Test the CLI plus the actual server handler and storage key, not just a client mock. No private signing seed belongs in fixtures or logs.

| Case | Required result |
| --- | --- |
| Projects A and B share one managed key; A has more rows than B | Their signed `agent_id` values match and `chain_id` values differ. Both push and fetch their own latest v2 anchor; both remote verifications pass at different row counts. The server stores two distinct verified pair keys. |
| Real rollback within A | After A's anchor advances, restore an earlier A DB snapshot while retaining its trusted ID. Push is rejected; fetch still returns A's newer anchor; verification fails `TRUNCATION`. B remains unchanged. |
| Forged chain identity | Change `chain_id` in signed JSON, URL, or local metadata without a valid matching signature/expected local ID. Push or verification fails before a row-count verdict; the store does not create or mutate a slot. |
| Swapped project anchor | Return B's valid signed anchor for A's URL, including a case where B has more rows. A fails identity verification, not `TRUNCATION`; B still verifies. Also reject URL/body pair disagreement at the server. |
| Missing or unreachable anchor | V2 remote verification exits non-zero as unavailable; ordinary push cannot recreate a missing enrolled slot. There is no local-only success fallback. |
| Legacy and migration | V1 signature verification still works explicitly. New client against old store fails without downgrade; old client against new store retains v1 behavior only before that key has a v2 stream, then fails on the frozen v1 route. Wrong-project, truncated, divergent, stale-digest, and duplicate-claim migrations fail with legacy and v2 rows unchanged. The correct explicit migration succeeds, freezes ordinary v1 access, and v2 verification passes. An existing unanchored DB enrolls only through the acknowledged one-time path; ordinary push/verify never invents its ID. |
| Prune after anchor | `log --prune` on an enrolled or registration-pending v2 chain is refused before any row changes, with the DB and remote pin unchanged; B is unaffected. The same command on an unenrolled/legacy chain, or on a chain with a `chain_id` and state none with a present identity record, still prunes only if no original registration request is retained; it is refused when `events.db` has a `chain_id` and the trusted record is missing. Lost response, then a retry that gets "already exists": enrolled, prune refused. Lost response (timeout, dropped connection, or crash before the marker) with no retry: pending, prune refused. Store rejects on a validation error: still pending, prune refused, and the error tells the operator to archive the old DB and enroll a fresh chain. |
| Rename, move, or clone | Moving DB and identity record preserves the pair and verification, including a legacy DB located inside the project with its identity record in trusted external state. Missing identity record fails. A deliberate fork gets a new ID; an accidental copied ID with divergent history conflicts instead of replacing the first stream. |

The v2 protocol, client and server implementation now support independent chains sharing one key; the one-chain-per-key limitation applies to legacy v1 clients and stores. The unreleased client requires explicit v2 enrollment or migration and an upgraded store. Actual handler/CLI coverage and its lower-level limits are recorded in the [acceptance runbook](../runbooks/anchor-v2-ncc-acceptance.md); this design is not a claim that every row above is exercised end to end.
