# Handoff: NockLock contributor notes

Every run reads this first and adds to it at the end. Keep it short and true: what changed, what bit us, what is still open. Maintainers prune it. Lasting lessons move into the gotchas in `AGENTS.md`; when an entry is only history, move it to a dated file in docs/archive (create the directory with the first one) and drop it from here.

No internal host names, personal names or absolute home paths: `scripts/check-public-content.py` scans this file like any other.

- 2026-10-26: Linux installer writes now propagate close failures; archive negative controls assert the intended refusal instead of any error. Rollback fixtures clear artifact input as the CLI does. The bootstrap recipe removes unauthenticated staging after failure, retains authenticated tools for recovery and explicitly sets the retained directory for helper setup.

Earlier releases have no managed upgrade or rollback path; v0.15.0 cannot be a managed rollback target. The installer does not support migration from source or candidate installations; the guide now directs users to a fresh host or the source-install workflow. Production signed-asset acceptance and publication remain outstanding.

The roadmap keeps v0.15.0 as the published baseline and the Linux installation bar open. Still open: promotion and tagging, production signed-asset acceptance, cross-version upgrade/rollback and broader network receipts, then immutable asset publication, Homebrew update and back-sync.

- 2026-10-26: standalone Linux installer implemented in `cmd/nocklock-install/` and `internal/linuxinstall/`: root-staged signature verification, immutable paired install, atomic activation, explicit-tag upgrade/rollback and opt-in generated helper authorization. `internal/installstate/` holds the permanent invocation/installer lock; managed CLIs refuse a stale executable after activation changes. - 2026-10-23: `verify --export ocsf [--out FILE]` (`internal/cli/verify_export.go`, mapping in `internal/ocsf/`) writes one OCSF 1.9.0 event per audit row plus a chain-evidence trailer, after the `verify --audit` checks pass; it refuses and writes nothing otherwise. The golden export is `internal/cli/testdata/ocsf/export.golden.jsonl`: regenerate it with `go test ./internal/cli -run OCSFExportGolden -update-ocsf-golden` and review the diff. CI validates the golden with `scripts/check-ocsf-schema.py`, which downloads the class schemas (the schema server can take over a minute per class) into a cached directory and pins them by SHA-256; bump the version and digests together. The export also refuses when the log gains rows between the `verify --audit` checks and its read (head hash compared; test seam `exportAfterChecks`), so exporting during an active wrap can need a re-run. The second chain walk is what gives that guarantee, so `--walk-timeout` applies to each walk. The trailer's `unsigned_through_id` and the documented head-bytes layout let late-adopted logs verify from the export; `internal/cli/verify_export_test.go` holds the outside-reader check. Still open: the export is built in memory, and the schema step needs PyPI and the schema server on a cold cache. Review follow-ups: `process.name` is the executable's base name (the quoted `command=` value is argv[0] alone and is never split; the older bare form takes its first word); a non-UTF-8 `detail` turns each maximal run of invalid bytes into one U+FFFD (`strings.ToValidUTF8`), which is the reader rule in `docs/how-it-works/audit-log.md`; `--out` is refused when it resolves (after symlinks, names compared case-insensitively) to the audit database, its `-wal`, `-shm` or `-journal` file, its `chain-anchor.json`, the managed signing key, or a trusted chain identity file (`chain-identity.json`, its lock, `anchor-registration.json`) (`refuseProtectedOut`). The schema check deletes a cached schema whose digest mismatches and downloads it once more; only a fresh download that mismatches fails (`scripts/test_ocsf_schema_cache.py`).

## What bit us

- 2026-10-26: config-digest tests use the checkout directory in filesystem grants. On macOS, a checkout under the protected home .codex directory correctly triggers credential-overlap refusal. A checkout under /tmp also puts the preset fixtures' fake homes beneath a default allow and triggers the same protection. Run those tests from a disposable source copy in an ordinary development directory; do not relax the policy to accommodate the checkout.

- 2026-10-23: the macOS credential proof (`scripts/test-credential-denies.py`) still set only `project.runtime` and wrapped `/bin/sh`, so it failed once that key stopped unlocking a login store. It now wraps with `--profile <agent>` for the own-store read and asserts `project.runtime` alone keeps the store denied.

- 2026-10-22: mandatory credential denies make a fake home beneath /tmp incompatible with the default /tmp allow, and root=/ is now refused even in network-only fixtures. CLI fixtures keep fake homes beside the package and network proofs grant their temporary project plus runtime paths.

- 2026-10-17, on a dev host: `go test ./...` failed in `internal/logging` under umask 002. The failure in `TestWrapComposedDefaultEgressAudit` was suspected to involve a week-old installed binary used by the egress helper; that host cause was not reverified. Both conditions are now `AGENTS.md` gotchas.

## Still open
